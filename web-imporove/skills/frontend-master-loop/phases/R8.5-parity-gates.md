# R8.5 — Parity Gates

## Purpose
Run ALL parity gates after migration to ensure the new code matches the old in a11y, seo, i18n, analytics, and integrations.

## Inputs
- All parity guard scripts
- Old and new route responses
- Golden test references

## Outputs
- artifacts/redesign/parity/PARITY_REPORT.json

## Steps
1. Run a11y gate (a11y-gate.sh) on all migrated routes.
2. Run seo gate (seo-gate.sh) on all migrated routes.
3. Run i18n parity (i18n-parity.sh) on all migrated routes.
4. Run analytics parity (analytics-parity.sh) on all migrated routes.
5. Run integrations parity (integrations-parity.sh) on all migrated routes.
6. Run observability parity (observability-parity.sh).
7. Aggregate all results into PARITY_REPORT.json.

## Verification Checklist (15+)
1. a11y gate passes for all routes.
2. seo gate passes for all routes.
3. i18n parity passes for all locales.
4. Analytics parity passes for all events.
5. Integrations parity passes for all endpoints.
6. Observability parity passes.
7. No critical violations in any gate.
8. Warnings documented.
9. Exemptions explicit with rationale.
10. PARITY_REPORT.json passes JSON.parse.
11. Each gate ran against both old and new.
12. Delta between old and new < 10%.
13. No new violations introduced.
14. All exemptions pre-approved.
15. Report includes per-route breakdown.

## Failure Modes
- Gate failure -> HST-03 (security), HST-10 (a11y), etc.
- Gate missing -> log warning, use parity guard script from guards/.
- Inconclusive result -> re-run (max 3 attempts).

## Checklist
1. All outputs written to artifacts/redesign/.
2. Phase report JSON validates with JSON.parse.
3. No secrets, credentials, or API keys in any output.
4. Phase results are append-only — previous phases preserved.
5. STATE.json updated with completion record and timestamp.
6. Any guards that ran returned exit code 0.
7. Artifacts are committed to the redesign branch only.
8. Cross-reference to parent APPROVALS.json is valid.
9. Data integrity verified (checksums match baseline).
10. Observability metrics recorded for this phase.
11. Rollback procedure documented in HARD_STOP report if triggered.
12. All temporary files cleaned up after completion.
13. Git diff examined for unexpected changes.
14. Size delta of codebase tracked.
15. Phase result logged to structured audit log.

## Rollback
- Read the corresponding rollback playbook from references/rollback-playbook.md.
- For guard-triggered rollbacks: flip feature flag, revert git commit, restore backup.
- Full phase rollback available within 5 minutes via feature flag inversion.
- If self-heal fails after 3 attempts, write HARD_STOP report and halt.
