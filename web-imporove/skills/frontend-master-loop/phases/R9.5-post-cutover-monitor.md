# R9.5 — Post-Cutover Monitor

## Purpose
72-hour monitoring window after full cutover. Error budget tracking, automated regression detection, and rollback triggers.

## Inputs
- APM/observability data stream
- CANARY_LOG.json
- BASELINE_METRICS.json from R1

## Outputs
- artifacts/redesign/monitor/MONITOR_LOG.json (updated every 6h)
- artifacts/redesign/monitor/SLO_REPORT.json

## Steps
1. Start 72h monitoring timer.
2. Every 6h, check:
   - Error rate vs baseline.
   - Latency p95 vs baseline.
   - SLO error budget consumption.
   - HST triggers.
3. If error budget consumption > approved %, auto-rollback.
4. If any HST fires, aut-rollback and HST report.
5. After 72h, write SLO_REPORT.json.
6. If all clear, confirm cutover stable.

## Verification Checklist (15+)
1. 72h monitoring window started.
2. Error rate checked every 6h.
3. Latency checked every 6h.
4. SLO budget consumption tracked.
5. No regression > 5% detected.
6. No new errors introduced.
7. All parity gates re-checked after 24h.
8. Cost delta within budget.
9. Rollback still possible (flag not removed).
10. Monitoring produces log.
11. SLO_REPORT.json passes JSON.parse.
12. MONITOR_LOG.json passes JSON.parse.
13. All findings documented.
14. Cutover stable confirmed.
15. Next step (cleanup or extend monitor) documented.

## Failure Modes
- SLO budget exhausted -> HST-02, auto-rollback.
- New regression detected -> rollback affected route.
- Monitoring data unavailable -> log diagnostic.

## Checklist
1. Continuous error rate monitoring active (5-min sliding window).
2. Latency p50/p95/p99 tracked against performance budget.
3. Resource utilization alerts configured (CPU, memory, disk).
4. Business metrics dashboard confirms conversion/sales stable.
5. Synthetic transactions run every 1 minute on critical paths.
6. Real user monitoring (RUM) data aggregated hourly.
7. Security monitoring active for anomalous patterns.
8. Cost tracking compares actual spend vs approved budget.
9. Backup jobs confirmed running on schedule.
10. Log retention policy enforced (30-day minimum).
11. Weekly review meeting scheduled with stakeholders.
12. Incident response playbook updated for post-cutover ops.
13. Auto-cleanup job queued for post-monitoring phase.
14. Migration success criteria documented and tracked.
15. Post-mortem template ready if issues arise during monitoring.

## Rollback
- If monitoring reveals degradation, trigger rollback immediately.
- Preserve all monitoring data for post-mortem analysis.
- Write detailed findings report documenting what went wrong and why rollback fired.
